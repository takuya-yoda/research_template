# plan/design — プログラムの要件定義と設計

アイデアを実装可能なコード設計まで落とすための作業場所。1 案件 = 1 フォルダ。

| 場所 | 内容 | 粒度 |
|---|---|---|
| `plan/research_plan.md` | 研究全体の目的・スコープ・マイルストーン | 研究 1 本 |
| `plan/design/<案件名>/requirements.md` | 何を満たせば完成かの定義 (目的・要求 → 各要件 → 受入基準 → 妥当性確認) | プログラム 1 案件 |
| `plan/design/<案件名>/design.md` | 要件をどう満たすかの設計 (設計方針 → 処理フロー → 構成 → テスト設計 → 実装計画) | プログラム 1 案件 |
| `code/src/<パッケージ名>/` | 設計に基づく実装 | モジュール |

`research_plan.md` の「やること」から派生した個々のプログラムがここに来て、
設計が固まったものが `code/` の実装になる、という流れを想定している。

要件定義書と設計書を分けているのは、**変更の理由が違う**ため。
要件定義書は「何を作るか」が変わったときだけ書き換わり、設計書は実装方針を変えるたびに書き換わる。

## 使い方

```bash
mkdir -p plan/design/<案件名>
cp plan/design/_requirements.md plan/design/<案件名>/requirements.md
cp plan/design/_design.md       plan/design/<案件名>/design.md
```

- 各見出しの直下にある **タグ行**（`記入: 人間` `必須` `派生元: ...`）が、その節を誰がいつ書くかを示す。記入後も消さない
- `記入: 人間` の節には `<!-- 問: ... -->` が置いてある。白紙を埋めるのではなく、この問いに答える
- 雛形内のその他の HTML コメントは記入の手引き。レンダリングされないので消さなくてよい
- `（例:...）` 行と各表の例行は書き方の見本。蔵書検索と強化学習の 2 例を並走させてある。記入時に削除する
- 設計の決定事項・方針変更は `plan/log.md` にも日付付きで 1 行残す（詳細はこちらのファイルへ）
- 議論を経て決めた設計は `plan/discussions/YYYY-MM-DD_<トピック>/` と日付で相互参照する
- 実装に着手したら設計書 15 節「実装計画」のタスクの状態を更新し、設計と実装がずれたら**設計書を書き換える**
  （設計書は実装後の現状を表す文書として維持する。履歴は git に残る）

## 役割分担

27 節すべてを人間が書くと時間がかかりすぎる。節は性質で 3 種に分かれ、後ろ 2 種は人間の手から外せる:

- **決定** — 人間しか出せない。削ると「コードの全容を把握しながら開発する」効果そのものが消える
- **派生** — 他節から機械的に決まる（雛形自身が「構成は処理内容から決まる従属変数」と書いている）
- **重複・同期** — 同じ ID が複数箇所に現れ、直すたびに全箇所の同期が要る

**誰が書くか**

| ラベル | 意味 |
|---|---|
| `記入: 人間` | 節内の「問:」に答える形で書く。Claude に代筆させない |
| `記入: Claude` | 派生元から Claude が下書き → 人間はレビューのみ |
| `記入: 自動` | 他節・実装・grep から生成する。手で書かない |
| `記入: 定型` | テンプレ既定またはプロジェクト共通の値をそのまま使う |

**いつ書くか**

| ラベル | 対象 |
|---|---|
| `必須` | 使い捨ての探索コードでも書く |
| `引継想定の場合は記入` | 半年後の自分・他人が引き継ぐ案件 |
| `公開想定の場合は記入` | 公開・共同開発する案件 |

**★ は死守する。** 処理フロー (設計 4 節) と ADR (設計 13 節) を Claude に書かせた時点で、
この分担は失敗する。前者は 5〜8 節の親であり、ここを人間が持っている限り全体像が保たれる。
後者は却下した案と理由であり、コードから復元できない唯一の情報である。

## どこまで書くか

判定は 1 問。**「半年後の自分以外がこのコードを引き継ぐか」**

| 案件 | 書く範囲 |
|---|---|
| 使い捨ての探索コード（〜200 行） | `必須` の 5 節のみ（要件 1・4・6・8・10）。設計書は作らず、決めたことは `plan/log.md` へ 1 行 |
| 引き継ぐ案件（研究コードの標準） | `必須` + `引継想定の場合は記入` |
| 公開・共同開発する案件 | 全節 |

## 読む順序と記入順序

**見出し番号は読む順序であり、記入順序とは一致しない。**
設計は合理的な順序では進まないが、文書は合理的な順序で書く（Parnas & Clements 1986。参考文献を参照）。
各文書の冒頭コメントに記入順序と Claude 生成順序を書いてある。

1. `requirements.md`: **1 → 4 → 6 の正常系 → 7 の数値 → 8**（人間）を先に書き、残りを Claude に下書きさせる。
   4 節「用語定義」を先に固定すると以降の要件が曖昧にならない。11 節のチェックが埋まらないうちは設計に進まない
   （8 節「除外要件」が空の案件はスコープ未確定のサイン）
2. `design.md`: **1 → 3.1 → 4 処理フロー**（人間）まで書いたら、**15.1 節の手順で空実装とテストを置く**。
   5・6・8 節は紙の上で決めず、そのコードから転記する
3. 残り（7・9〜12・15.2）を Claude に下書きさせ、1 段ずつレビューする。14 節は grep で生成する

参照は一方向に流す: `design.md` は `requirements.md` を参照してよいが、逆は書かない。

## 受入基準と pytest

受入基準 (AT-XX) の唯一の正は **`requirements.md` 10 節**（実装前に書けるのは文書だけのため）。
実装に着手したら pytest のテストコードが正になる:

```python
def test_AT01_search_partial_match():   # 関数名に AT-ID を埋める
    ...
```

- `pytest -k AT01` で個別に実行できる
- 設計書 14 節の対応表は、この ID を grep して生成する（手で書かない）
- pytest 以外で実行する受入基準（負荷試験など）は、実行コマンドをテスト関数の docstring に書く
- 設計書 12.3 節に受入テストの表を作らない

## 版を重ねる場合

- 実装との小さなずれ → **同じファイルを書き換える**（設計書は実装後の現状を表す文書として維持する）
- 新しい受入基準を持つ開発ラウンド → **新フォルダ** `<案件名>_v2/` を起こす。
  前版から引き継ぐもの（除外要件の「将来の扱い」、設計書 15.3 節の未実施 PoC、ADR の帰結）を転記し、
  前版は完了時点の姿で凍結する

## 運用の予定（試用中）

**役割分担のタグと記入順序を導入した改訂版。**
引き続き使用時のフィードバックで磨く方針のため、当面は次のように扱う:

- 見出しは自由に増減してよい。案件に合わない見出しは削ってよいし、必要な観点は足してよい
- 「この見出しが要る / 要らなかった」「タグの割り当てが実態と違った」と気づいたら `plan/log.md` に 1 行記録する
  （`_requirements.md` / `_design.md` や この README を直接編集すると、テンプレート更新の取り込み時に衝突する）
- 案件を終えたら所要時間も 1 行残すと、どの節が効いているかを測ってから削れる
  （例: `要件 40分 / 設計 90分 / 後で読み返した節: 3.1, 13 / 読まなかった: 2, 11`）
- 記録が集まった段階でテンプレート側 (research_template) の雛形を改訂し、
  `copier update` で各プロジェクトへ配信する。そのとき見出し構成が変わりうる
- 既に書いた `<案件名>/` の中身は雛形の改訂に追随しなくてよい（コピー後は各プロジェクトの持ち物）
