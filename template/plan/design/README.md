# plan/design — プログラムの要件定義と設計

アイデアを実装可能なコード設計まで落とすための作業場所。1 案件 = 1 フォルダ。

| 場所 | 内容 | 粒度 |
|---|---|---|
| `plan/research_plan.md` | 研究全体の目的・スコープ・マイルストーン | 研究 1 本 |
| `plan/design/<案件名>/requirements.md` | 何を満たせば完成かの定義 (目的・要求 → 各要件 → 受入基準 → 妥当性確認) | プログラム 1 案件 |
| `plan/design/<案件名>/design.md` | 要件をどう満たすかの設計 (設計方針 → 処理フロー → 構成 → テスト設計 → 実装計画) | プログラム 1 案件 |
| `code/src/<パッケージ名>/` | 設計に基づく実装 | モジュール |

`research_plan.md` の「やること」から派生した個々のプログラムがここに来て、
設計が固まったものが `code/` の実装になる、という流れを想定している。

要件定義書と設計書を分けているのは、**変更の理由が違う**ため。
要件定義書は「何を作るか」が変わったときだけ書き換わり、設計書は実装方針を変えるたびに書き換わる。

## 使い方

```bash
mkdir -p plan/design/<案件名>
cp plan/design/_requirements.md plan/design/<案件名>/requirements.md
cp plan/design/_design.md       plan/design/<案件名>/design.md
```

- 雛形内の HTML コメントは記入の手引き。レンダリングされないので消さなくてよい
- `（例:...）` 行と各表の例行は書き方の見本。蔵書検索と強化学習の 2 例を並走させてある。記入時に削除する
- 設計の決定事項・方針変更は `plan/log.md` にも日付付きで 1 行残す（詳細はこちらのファイルへ）
- 議論を経て決めた設計は `plan/discussions/YYYY-MM-DD_<トピック>/` と日付で相互参照する
- 実装に着手したら設計書 15 節「実装計画」のタスクの状態を更新し、設計と実装がずれたら**設計書を書き換える**
  （設計書は実装後の現状を表す文書として維持する。履歴は git に残る）

## 書く順序

**requirements.md を先に、design.md を後に**書く。見出し順 = 記入順で、後から変えにくい決定ほど先に固定する並びになっている:

1. `requirements.md` の **1〜11 節**を上から埋める。4 節「用語定義」を先に固定すると以降の要件が曖昧にならない。
   11 節「妥当性確認」のチェックが埋まらないうちは設計に進まない
   （8 節「除外要件」が空の案件はスコープ未確定のサイン）
2. `design.md` の **1〜16 節**を冒頭コメント「記入順序」の 4 段階に従って埋める。
   要は処理フロー（4 節）から構成（7・8 節）を導くこと。ここで固定するのは変えにくい決定（3.1 節）だけで、
   可逆な決定は実装中に決めてよい
3. **テスト設計（12 節）**は受入基準 (AT-XX) と対応させ、実装は 15.1 節の着手順序
   （空実装とテストを先に置き、全テストが失敗する状態から依存の下位層順に実装する）に従う

参照は一方向に流す: `design.md` は `requirements.md` を参照してよいが、逆は書かない。

## 版を重ねる場合

- 実装との小さなずれ → **同じファイルを書き換える**（設計書は実装後の現状を表す文書として維持する）
- 新しい受入基準を持つ開発ラウンド → **新フォルダ** `<案件名>_v2/` を起こす。
  前版から引き継ぐもの（除外要件の「将来の扱い」、設計書 15.3 節の未実施 PoC、ADR の帰結）を転記し、
  前版は完了時点の姿で凍結する

## 運用の予定（試用中）

**見出し構成は実運用プロジェクトの設計文書の調査を反映した改訂版。**
引き続き使用時のフィードバックで磨く方針のため、当面は次のように扱う:

- 見出しは自由に増減してよい。案件に合わない見出しは削ってよいし、必要な観点は足してよい
- 「この見出しが要る / 要らなかった」と気づいたら `plan/log.md` に 1 行記録する
  （`_requirements.md` / `_design.md` や この README を直接編集すると、テンプレート更新の取り込み時に衝突する）
- 記録が集まった段階でテンプレート側 (research_template) の雛形を改訂し、
  `copier update` で各プロジェクトへ配信する。そのとき見出し構成が変わりうる
- 既に書いた `<案件名>/` の中身は雛形の改訂に追随しなくてよい（コピー後は各プロジェクトの持ち物）
