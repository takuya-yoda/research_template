# plan/design — プログラムの設計メモ

アイデアを実装可能なコード設計まで落とすための作業場所。1 案件 = 1 ファイル。

| 場所 | 内容 | 粒度 |
|---|---|---|
| `plan/research_plan.md` | 研究全体の目的・スコープ・マイルストーン | 研究 1 本 |
| `plan/design/<案件名>.md` | プログラム 1 案件の設計 (目的 → 完了条件 → 設計 → 実装計画) | プログラム 1 案件 |
| `code/src/<パッケージ名>/` | 設計に基づく実装 | モジュール |

`research_plan.md` の「やること」から派生した個々のプログラムがここに来て、
設計が固まったものが `code/` の実装になる、という流れを想定している。

## 使い方

```bash
cp plan/design/_template.md plan/design/<案件名>.md
```

- 雛形内の HTML コメントは記入の手引き。レンダリングされないので消さなくてよい
- `(例)` 行は書き方の見本。記入時に削除する
- 原因究明 (バグ・数値不一致の診断) の案件も同じ雛形を使う。「設計」「実装計画」のコメントにある読み替えに従う
- 設計の決定事項・方針変更は `plan/log.md` にも日付付きで 1 行残す（詳細はこちらのファイルへ）
- 議論を経て決めた設計は `plan/discussions/YYYY-MM-DD_<トピック>/` と日付で相互参照する
- 実装に着手したら「実装計画」のチェックボックスを進め、設計と実装がずれたら**このファイルを書き換える**
  （設計メモは実装後の現状を表す文書として維持する。履歴は git に残る）

## 書く順序

見出し順 = 記入順。後から変えにくい決定ほど先に固定する並びになっている:

1. **目的 → 完了条件 → 範囲外** でスコープを固める。スコープの決定が以降の全章を縛る
   （「範囲外」が空の案件はスコープ未確定のサイン）
2. **設計**は節を上から順に埋める（仕組み → モジュール構成 → データ構造・インタフェース → 設計判断）。
   ここで固定するのは変えにくい決定だけ。可逆な決定は実装中に決めてよい
3. **検証方法 → 実装計画** は上の章から導く。実装計画の最初に最小の縦貫
   （入力→出力が一度通る骨格）を置くと、以降の各段が動くものへの追加になる

## 版を重ねる場合

- 実装との小さなずれ → **同じファイルを書き換える**（設計メモは実装後の現状を表す文書として維持する）
- 新しい完了条件を持つ開発ラウンド → **新ファイル** `<案件名>_v2.md` を起こす。
  前版の「据え置き・懸念」から引き継ぐものを転記し、前版は完了時点の姿で凍結する

## 運用の予定（試用中）

**見出し構成は実運用プロジェクトの設計文書の調査を反映した改訂版。**
引き続き使用時のフィードバックで磨く方針のため、当面は次のように扱う:

- 見出しは自由に増減してよい。案件に合わない見出しは削ってよいし、必要な観点は足してよい
- 「この見出しが要る / 要らなかった」と気づいたら `plan/log.md` に 1 行記録する
  （`_template.md` や この README を直接編集すると、テンプレート更新の取り込み時に衝突する）
- 記録が集まった段階でテンプレート側 (research_template) の `_template.md` を改訂し、
  `copier update` で各プロジェクトへ配信する。そのとき見出し構成が変わりうる
- 既に書いた `<案件名>.md` は雛形の改訂に追随しなくてよい（コピー後は各プロジェクトの持ち物）
