# ドメイン文書

エンジニアリング系のスキルが、コードベースを調べるときにこのリポジトリのドメイン文書をどう読むかを定める。構成は single-context。

## 調べる前に読むもの

- ルートの **`CONTEXT.md`**: 用語集
- **`docs/adr/`**: これから触る領域に関わる ADR
- **`docs/research_plan.md`**: 研究全体の目的と範囲
- 物理式・アルゴリズムの正本（案件側で記入。コードの式はこの文書の式番号を参照する）:
  <!-- 例: `theory/<ノート名>/note.tex` -->
  -

ファイルが存在しない場合は黙って進める。用語や決定が実際に確定した時点で、`/domain-modeling`（`/grill-with-docs` 経由）が追記する。

## 構成

```text
/
├── CONTEXT.md
├── docs/adr/
│   └── NNNN-<slug>.md
└── code/
    ├── src/<パッケージ>/
    └── experiments/<YYYYMMDD>_<名前>/
```

## 用語集の語彙を使う

出力（issue の題名、リファクタリングの提案、仮説、テスト名）でドメインの概念を名指すときは、`CONTEXT.md` の定義どおりの語を使う。用語集が _Avoid_ に挙げる同義語へ流れない。

必要な概念が用語集に無い場合は、プロジェクトが使わない言葉を持ち込んでいるか（再考する）、本当に欠けているか（`/domain-modeling` に回す）のどちらかである。

## ADR との矛盾を明示する

出力が既存の ADR と矛盾するときは、黙って上書きせず明示する。

> _ADR-0001 と矛盾するが、〜の理由で再検討に値する_

## 用語集のファイル名

- 用語集は `CONTEXT.md` とする。導入済みのプラグイン（v1.2.3）がこの名前を読み書きする
- upstream は v1.3.0 で規約を `GLOSSARY.md` に改名した。プラグインを上げるときは雛形（research_template）側で一括して改名する。`GLOSSARY.md` を個別に作らない
